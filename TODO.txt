sjasmplus developer TODO and design notes
=========================================

This is a working notebook, not a release plan or a specification. Items are
grouped by subject, not ordered by priority. Check current code, tests and docs
before implementing an old note; uncertain behavior below is not a confirmed bug.
docs/documentation.xml is the source of truth for documented assembler syntax.

Item status:
    [Task]       A concrete change or test to investigate and implement.
    [Research]   Confirm the problem and scope before choosing a change.
    [Idea]       An undecided proposal, possibly incompatible with existing sources.
    [Historical] Implemented work or old design context, retained for reference.
    [Checklist]  Recurring maintainer work, not an assembler feature.


Parser, syntax and safety
=========================

[Task] Complete numeric C-style string escapes
    Original note: octal \nnn and hexadecimal \xn... escapes are still missing.
    Verify current support and define how many digits each form consumes before
    implementation; preserve existing literal syntax unless deliberately changed.
    Reference: https://en.cppreference.com/w/c/language/escape

[Research] IN/OUT bracket syntax
    Check Z80 IN/OUT operands with [] and with --syntax=B (brackets-only mode).
    The original observation was that only (c) and (n) worked. Establish the current
    behavior with tests before treating this as a parser defect.

[Task] Test expression operator groups and precedence
    Start in parser.cpp, at ParseExpShift and the operator parsers using "needa".
    Exercise repeated operators in their while loops, operator aliases and precedence.
    Investigate token transformations such as shr becoming '>'; the original note
    was a question, not a confirmed defect.

[Task] Implement --syntax=l and --syntax=L keyword-label diagnostics
    l should warn and L should error when a keyword (register, instruction, etc.) is
    used as a label. Both are documented as unimplemented; parseSyntaxValue() in
    sjasm/sjasm.cpp currently reports "Syntax option not implemented yet".
    Turn the documented example "hl: Ld a,(hl),,de,hl" into a docs example test once
    supported. Consult the --syntax description in docs/documentation.xml for the
    combined --syntax=faBil behavior. Lowercase i already controls case-insensitive
    instructions/directives; it does not make labels case-insensitive.

[Research] Simplify ParseDirective_REPT without breaking repeat directives
    Establish why this separate directive path exists before removing it.
    Suspected edge cases in the old note: " .34 repeatX" and END at beginning of
    line. Neither is a confirmed reproduction; add focused tests first.

[Research] Audit STRCPY/STRCAT size limits
    Maintainer concern: some maximum-size arguments may be incorrect, allowing
    buffer overflow on malicious source input. No specific failing call was recorded.
    Audit the wrapper contracts and callers, and retain reproductions as tests.

[Research] Review output filename validation and modification
    Review SAVEHOB/SAVETRD/SAVETAP and related directives. Warn or error where a
    filename is invalid or is modified, after deciding which modifications are
    intentional format behavior. This is a broader review, not a request to reject
    every transformed filename.


Output files, devices and loaders
=================================

[Idea] Fill gaps in raw output, or provide device-backed output
    Request from @Janko on Next Discord: --raw-fill-gaps should emit filler between
    ORG $2000 and a later ORG $2100 when using --raw (for example, building test.dot).
    Alternative requested by Janko: a new -o option enabling a plain 64K device and
    saving its assembled range, instead of treating output as a stream.
    A NOSLOT64K-like implicit device may help, but the written range must come from
    modified-region tracking or program-counter bounds, NOT scanning for nonzero
    bytes. Zero bytes can be intentional output. Output semantics remain undecided.

[Idea] APPENDBIN and large binary files
    Append an arbitrary-size binary to another file, e.g. data following a large
    dot command. Include GiB-scale support in the design. The original constraint
    noted for INCBIN was its int32 length limit (about 2 GiB) and loading the entire
    input into heap memory; verify those constraints before reusing its machinery.

[Idea] Reserve a block without changing existing device memory
    Provide a standalone block/reserve operation which advances the address while
    preserving device bytes. The original note contrasts DS/BLOCK with preserving
    behavior in structure blocks/alignment and standalone ALIGN.
    Check the current BLOCK/DS and structure semantics before choosing new syntax.

[Research] ZX Spectrum BASIC loader paging compatibility
    Inspect example loaders in examples/ and the snapshot-style SAVETAP loader,
    including any embedded machine-code blob. Determine whether they need changes
    for 48K BASIC, 128K BASIC or +3 BASIC; this is not a confirmed loader bug.
    Reference advice from baze to @neon on Discord:
        Keep LOAD in BASIC even if paging OUT instructions stay in machine code.
        Use "set 4,(iy + 1)" to avoid +3 BASIC corrupting page 7 during IM 1.
        After each "out (c),a", also do "ld (#5B5C),a" to keep 128 BASIC informed.
    Research and test the advice before applying it to any loader. Retain it as
    reference material even if the current examples turn out not to be affected.

[Research] Relocation support for ZX Next driver banks
    Determine the required bank relocation behavior from Robin's projects before
    designing an extension to sjasmplus relocation.
    References:
        https://github.com/Threetwosevensixseven/ZXRelocate
        https://github.com/Threetwosevensixseven/JetDPCL5/tree/main/src/asm/drv
        https://pastebin.com/4G5nf9qv

[Research] CSPECTMAP with DISP
    Identify and test the desired mapping of displaced addresses in CSPECTMAP.
    An older comparison with an external tool may have involved source without a
    DEVICE directive; distinguish that setup issue from actual export limitations.

[Idea] Extend MMU mapping options
    Allow a custom page order for next-page wrapping, e.g. "<3, 5, 1, 2>".
    Consider error/warning/wrapping options for a slot range, not only one slot.
    Check existing MMU support first; these are design questions, not fixed syntax.


Diagnostics and listings
========================

[Task] Control expansion/include trace verbosity
    Add a CLI option for the "emitted/included at/from" diagnostic trace messages,
    allowing quieter output in --msg=war or --msg=err mode. Decide independently
    which primary diagnostics and which trace lines should remain visible.

[Research] Show original source in "emitted from here" diagnostics
    Users without editor error parsing found the existing message confusing or
    unhelpful. Include the relevant original source line if practical.
    Previous investigation found macros and inline Lua make this harder than a
    simple formatting change; preserve the correct source/expansion attribution.

[Idea] Include the original pre-substitution line in listings
    Cover DUP/EDUP expansion and colon-separated instructions such as nop:nop:nop.
    Possible presentation: '<' as a counterpart to macro '>', line number but no
    address. Choose the format before implementation; this is not settled syntax.

[Idea] Syntax highlighting rules for generated listing files
    Investigate whether assembler highlighting can apply to only the source-code
    portion of a listing line, separately from addresses, bytes and diagnostics.

String operators and substitution design
========================================

[Idea] String operations in expressions
    Consider Lua-like concatenation ("..") and length (#"str"), perhaps implemented
    in quoted-string parsing. Define the boundary between numeric character
    constants and strings before adding operators.
    Existing expressions such as ld hl,"ab" + "cd", ld hl,"ab"|128 and
    ld hl,"ab"+128 are compatibility cases. Do not silently reinterpret them as
    string operations. Operator choice and type/coercion rules remain undecided.

[Idea] Macro-defined operators and expression introspection
    Allow macros to define operators rather than only instruction-like constructs.
    Motivating example: could an operator like zeuskeyaddr be recreated with a
    macro? The required semantics/example still need specifying.
    Also consider string manipulation, islabel-like type/expression checks and
    variadic facilities. These are exploratory language extensions.

[Idea] Uppercase/case-insensitive label handling
    Original proposal: --syntax=I would uppercase label definitions and references;
    this would require label-handling refactoring. No such implemented option is
    established by this note. Keep separate from existing --syntax=i and the
    proposed l/L keyword-label diagnostics.

[Research] Remaining macro/DEFINE substitution proposals
    Current rules are documented in docs/documentation.xml, "Substitution and
    Defines". Macro arguments have precedence over defines/defarrays, may substitute
    in define-related directives, and a leading underscore restricts matching to
    the beginning of an identifier. Matching is NOT specified as longest-first.
    Remaining questions from the older proposal:
        - Should competing macro arguments/defines match longest-first?
        - Should a trailing underscore restrict matching at the end as well?
        - Should reserved keywords be protected from DEFINE, or produce a warning?
        - Should substitution have an explicit inhibitor, analogous to @djnz
            inhibiting macro replacement?
    Add tests and assess compatibility before changing the current deterministic
    matching order. The old comparison with behavior around v1.08 is historical,
    not a description of a newly pending refactor.


Possible 2.x changes / incompatible fork
========================================

These are undecided proposals, not commitments. Create focused GitHub issues
under the v2.x milestone when scope is clear, and remove duplicate notebook items.
The intended compatibility break could be larger than the v1.07 to v1.14 changes.

[Idea] More than three assembly passes (N-pass assembling)
    No convergence rules, pass limit or failure behavior have been specified here.

[Idea] Stricter defaults and C++-like expression/literal rules
    Revisit defaults; the old sketch was --syntax=abflL, but l/L are alternative
    warning/error policies, so the exact combination must be decided, not copied.
    Review other relaxed/ambiguous syntax and operator precedence.
    Original precedence question: (2 == 3&2) == ((2 == 3)&2) == false.
    Establish actual/intended behavior with discriminating tests before changing it.
    Reference: https://en.cppreference.com/w/cpp/language/operator_precedence
    Consider a word/w16/i16 truncation operator, analogous to low.
    Review escaped apostrophes and other character/string literal combinations;
    C/C++ escapes are case-sensitive, unlike the behavior described in the old note.

[Idea] Separate ordinary local labels from macro-local labels
    Consider a distinct macro-local prefix, perhaps '>'. See issue #120.

[Idea] Physical versus slot-mapped label addresses
    Represent a label with 2 or 3 high bits for its default slot and the remaining
    30 or 29 bits for a physical address; machine-code emission would map that
    physical address into a selected slot.
    Compatibility problem: ordinary 0000..FFFF mapped addresses collide with early
    physical pages. Consider explicit notation rather than silently changing them.
    Undecided sketches: @ or . distinction; &label/expression as in C/C++;
    <slot>$$expression as a binary slot-remapping operator.
    Distinguish addresses wider than 16 bits from the 16-bit slot-mapped view.

[Idea] Nested DISP blocks
    Existing DISP-inside-DISP limitations/bugs were documented in the old note.
    Determine whether nesting is the right solution rather than assuming it is.

[Idea] Change SHELLEXEC syntax
    See dirSHELLEXEC in sjasm/directives.cpp: the proposed direction is raw command
    text instead of separate <command>[, <params>]. Work out quoting, colons and
    filenames with spaces before changing the grammar.

[Idea] Toolchain-style CLI, paths and diagnostics
    Follow GNU/GCC/Clang conventions where practical, including diagnostic formats
    and equivalent option syntax, to work with existing editor/build integrations.
    Consider GCC-like include-path anchoring from the launch/main-file directory,
    instead of changing the anchor with every included source file.
    Review cross-platform filesystem APIs and slash handling. The old note proposed
    POSIX/C-library APIs; reassess against the current filesystem implementation.

[Idea] Additional language/tool integration
    Better support for Maziac's tools, e.g. label-type export; requirements need
    specifying with the consuming tools.
    JavaScript scripting support was suggested, but no concrete use case or scope
    was recorded. Keep as an idea, not an implementation task.
    Further substitution formalization and new operators are covered above.


Debian packaging
================

[Checklist] Build against system libraries
    CMake is used to enforce/test system-library builds. Historical invocation
    (from a build directory):
        cmake -DCMAKE_BUILD_TYPE=Release -DSYSTEM_LUA=ON -DCMAKE_INSTALL_PREFIX:PATH=~/.local2/ ..
    For documentation-generation dependencies and validation, see docs/README.md.

[Checklist] Generate the cleaned source archive for Debian packaging
    The gen-dfsg-tarball branch in this official repository provides the cleaned
    archive, excluding tests with incompatible or unclear licensing and retaining
    the intended open-source files. Use that branch's archive-generation workflow;
    the original repacking research task is no longer pending.
    None of the removed files contribute to the final executable, so the cleaned
    archive still builds the fully featured sjasmplus binary.
    References:
        https://www.debian.org/doc/manuals/distribute-deb/distribute-deb.html
        https://wiki.debian.org/Packaging/Learn#Level_3:_Packaging_more_complicated_modules

Historical notes / syntax scratchpad
====================================

[Historical] $$label page operator and label parsing refactor
    Implemented according to the original note, including work on DEFL/EQU and
    expression-label pages, label parsing and validation. This is not a new task.
    The note was retained to watch for regressions; remove when no longer useful.
    Rejected/older spellings:
        ?label: ambiguous in 5<?label; an old undocumented '?' label operator was
            described as deprecated. Verify current support before relying on that.
        \label: no obvious syntax clash, but $$label was chosen instead.

[Historical] Syntax sketch, NOT an authoritative grammar
    Retained as context for operator/label design. Check the manual and parser for
    the full current grammar; this shorthand may be incomplete or outdated.
        (\.|\!?@|)[A-Za-z_][A-Za-z0-9_.?!#@]* labels, \\ continue line (limited!)
        , argument separator; : instruction separator; ; and // comments
        # $ hex numbers; % binary; ' _ numeric group separators
        " ' strings; () parentheses or memory; [] memory; {} device memory
        unary: ! ~ + - low high not abs norel exist
        binary: * / % mod + - << >> >>> shl shr <? >? < > <= >= = == != & and ^ xor | or && ||
        US keyboard characters: ~!@#$%^&*()_+`-=[]{};':"<>?,./\|
